## 4. Decisions & Reasons

- **Dropdown menu instead of a centered dialog:** profile info is small and contextual; a menu opens right under the avatar (as requested: image/avatar click → menu).
- **No new npm dependency for theme:** small toggle adds/removes the `dark` class on `<html>` and saves the choice in `localStorage`. Icon switches via CSS (`dark:hidden`), so there is no hydration mismatch.
- **Role values:** `students` (UI: Student) / `teachers` (UI: Teacher) / `admin`. `seeker`/`recruiter` are gone. Mapping is inlined in each component (the old `src/lib/roles.ts` was deleted) and legacy `student` / `teacher` values are still accepted for navigation.

- **Navbar icons + Dashboard shortcut:** each nav link carries its own `icon` in the `navLinks` array; logged-in users see a role-based Dashboard button in the navbar and mobile sheet.
- **Client typed via `inferAdditionalFields<typeof auth>()`:** this is the BetterAuth way to make `signUp.email({ role })` and `session.user.role` type-safe without duplicating the field list. Uses `import type`, so server code is not bundled into the client.
- **Unknown/missing role no longer falls back to `students`:** it resolves to `null` and routes to `/` (home), so a broken role cannot silently open a dashboard. Known roles still map to their own dashboard, and legacy `student` / `teacher` are normalized for navigation only.
- **Browse tuitions is server-fetched:** the page calls the Express backend on the server (`cache: "no-store"`) and passes the list down; the client only filters. This keeps deployment working even when the browser cannot reach the API host directly.
- **Success page verifies with the backend:** when Stripe says the session is paid, the server page calls `POST /VerifyPayment` before rendering the receipt, so the plan is actually activated and the receipt is stored in `StudentAndTeacherPaymentsStutus`. A backend failure still shows the Stripe-paid UI with a fallback receipt ID instead of crashing.
- **Navbar and sidebar use Tailwind classes only** (teal/cyan neon), no theme token changes.
- **`/sign-in` needs `<Suspense>`** because `SignInPage` uses `useSearchParams()`; Next 16 fails the static build without it.
- **Navbar avatar uses the real image first:** `user.image` (ImgBB / Google / GitHub URL) is shown when present, and initials are only a fallback. Plain `<img>` is used because remote ImgBB domains are not configured for `next/image`.
- **Navbar only on home pages:** it lives in the `(home)` route group layout, so dashboard/auth pages stay clean. Rule: only the root layout may render `<html>`/`<body>`; a nested layout that renders them causes a hydration error.
- **Role mapping:** `students → Student (/dashboard/students)`, `teachers → Teacher (/dashboard/teachers)`, `admin → Admin (/dashboard/admin)`.
- **Footer is a client component** (`"use client"`) only because hugeicons icons use `forwardRef`; it has no state, so there is no behavior cost. Branding/copy is MentorLagbe with `hello@mentorlagbe.com`; social links are `#` placeholders until real profiles exist.
- **Nav links are future routes:** `/tuitions`, `/pricing`, `/about`, `/privacy`, `/terms` do not exist yet (404 until built).
- **Profile Add vs Edit is decided by data:** server page fetches first; `null` → `mode="add"` (POST), data → `mode="edit"` (PATCH with `_id`). One form component handles both, so no duplicate UI.
- **`Profile-Form.tsx` and `ImageFeild.tsx` were left untouched** (user's request). The original BetterAuth `name` / `image` / `coverImage` update flow still works exactly as before.
- **Teacher card is its own file** (`TeacherProfile.tsx`) so other pages can reuse `<TeacherProfileCard profile={...} />` without copying JSX.
- **`UserProfileCard` now receives `profile` as a prop** instead of fetching inside, so the page fetches once and the card stays a simple presentational component.
- **Admin does not get profile info forms** (`role === "admin"` skips the section), per the requirement that only student and teacher profiles work.
- **Old profile photo is preserved on edit** unless the user selects a new file: initial `photoURL` is used as the default value.
- **User card image fallback:** the circular avatar uses `profile.photoURL` first; if that is empty it falls back to the logged-in BetterAuth `user.image`, and finally to a gradient circle with the name's first letter. The auth image itself is never modified from the card.
- **User card image is a circle, not a banner:** an earlier full-width `h-56` top image was too wide/large, so it was replaced with a centered `h-24 sm:h-28` circular avatar (white ring + soft cyan glow + initial fallback). No fixed wide image area remains.
- **Responsive layout lives in the page wrapper:** `/profile` header stacks on mobile and cards switch to 2 columns from `md`. `ImageFeild.tsx` / `Profile-Form.tsx` were still not edited (user's earlier rule), so the main cover/avatar block keeps its own existing responsive classes.
- **"No info yet" message appears twice:** once as the dashed empty card on the page, and once as a yellow banner inside the Add Info dialog (`mode === "add"`). Edit mode never shows that banner because data already exists.
- **Details page is a public `(home)` route:** `/view/[id]` fetches the Express backend on the server (`cache: "no-store"`), so no client API key or CORS issue. The backend stores the raw `Tuitions` document and the page reshapes it into `TuitionDetailData` (fee formatted, status capitalised, `verificationStatus === "verified"` → mentor verified). Real 404s use `notFound()`; a network failure shows a "could not load" card instead of crashing.
- **`/view` (no id) redirects:** there is no list at that path, so it sends the user to `/browsetuitions`.
- **Closed tuitions are public-facing hidden, dashboard-visible:** the browse list requests `status=active` and the details page refuses to render a closed tuition (shows a "closed" card instead). The teacher dashboard keeps using `GET /TeacherTeutionsGet/:email`, so a tutor can still see and reopen closed posts.
- **Filtering happens on the client:** `/browsetuitions` fetches the active list once and filters in memory. This keeps select options (generated from the data) and results always in sync, and makes search instant. The backend filter upgrades (`classLevel` grouping, partial subject/mode) still exist for direct API/URL use.
- **URL params are read on the server:** `searchParams` → `initialSearch` / `initialMode` props, so nothing calls `setState` inside an effect (the `react-hooks/set-state-in-effect` lint rule fails the build otherwise).
- **Teacher page keyed by email:** the tuition document only stores `name` + `email` for the mentor (`mentorId` also exists but the public page URL is the email), so the public page is `/teacher/[email]` and resolves profile data with `GET /TeachersProfile/:email` / `GET /UsersGet/:email`. Name fallback chain: user profile → teacher's tuition `name` → prettified email.
- **Applications are server-validated:** `POST /ApplyPost` never trusts the client — it reloads the tuition by id, re-reads the real title/fee/mentor from the DB, refuses closed tuitions (409) and duplicate `(tuitionId, studentEmail)` pairs. The student email comes from the BetterAuth session (`ClientUser`), not from a form field, so nobody can apply as someone else.
- **One application per student per tuition:** duplicate applies return `409 You have already applied for this tuition` and the modal shows the backend message in the toast instead of a generic failure.
- **Apply requires sign-in:** the modal shows a **Sign in as a student** banner (link `/sign-in?callbackUrl=/view/<id>`) and disables the submit button; the backend also returns 401 for an empty student email.
- **Backend base URL fallback is always `http://localhost:8000`:** the old modal used `5000`, so Apply silently failed whenever `NEXT_PUBLIC_API_URL` was missing.
- **Plan status is derived from paid receipts, not from a cached date:** `UsersData.planExpiresAt` is only a cache written by `syncUserPlanFromReceipts`. Anything that can remove/undo a payment (`DeletePayment`, `UpdatePaymentStatus`, admin refunds) recomputes it, and `/GetPlanStatus` recomputes it on every read. This is why a student with no paid receipt can no longer get stuck on a disabled "Pro Pass Active" button, while a teacher who really paid keeps an active plan.

## 6. API / DB Notes

- BetterAuth user model has `additionalFields`: `role` (`students` | `teachers` | `admin`, default `students`) and `coverImage`.
- MongoDB database name: `assignment-projects` (see `src/lib/auth.ts`). Secrets stay in `.env` only.
- Express backend (`C:\projects\assignment-9-bk\index.js`, default port `8000`) collections:
  - `Profile` — user profile: `POST /UserProfiles`, `PATCH /UsersUpdate/:id`, `GET /UsersGet/:email`.
  - `Teacher-Address` — teacher profile: `POST /TeachersProfile`, `PATCH /TeachersUpdate/:id`, `GET /TeachersProfile/:email`.
  - Both GETs sort by `updatedAt` newest first and match `email` or `addedBy.email`.
- Frontend needs `NEXT_PUBLIC_API_URL` in `.env` (or it falls back to `http://localhost:8000`).
- `Tuitions` collection (backend already had these routes): `POST /TuitionsPost`, `GET /Tuitions`, `GET /AllTuitions`, `GET /TeacherTeutionsGet/:email`, `PATCH /Tuitions/:id/status`, `PATCH /TuitionsEdit/:id`, `PATCH /Tuitions/:id/verify`, `DELETE /TuitionsDelete/:id`. New tuition default: `status: "active"`, `verificationStatus: "pending"`.
- 2 test tuitions currently exist in `Tuitions` for `boltuvai@boltu.com` (ids `6b0082fbf918bc514a2e1ec2`, `6b0082fbf918bc514a2e1ec3`). Delete them from the dashboard or MongoDB Compass when no longer needed.
- Single tuition details: **`GET /Tuitions/:id`** (added; returns the raw document, 400 for invalid ObjectId, 404 when missing). The view page (`src/app/(home)/view/[id]/page.tsx`) calls it; `GET /Tuitions` filters are unchanged.
- `Applications` collection (new, for Apply Now):
  - `POST /ApplyPost` — body: `{ tuitionId, studentName, studentEmail, studentId?, phone?, sessionTime?, message? }` (+ client-sent title/fee that the server overwrites from the DB). 201 on success, 400 invalid tuitionId / missing name, 401 no email, 404 unknown tuition, 409 closed tuition or duplicate application.
  - `GET /ApplyGet/:email` — student's applications (newest first).
  - `GET /TeacherApplicationsGet/:email` — all applications for a teacher's tuitions.
  - `GET /Tuitions/:id/applications` — applications of one tuition.
  - `PATCH /ApplyStatus/:id` — `{ status: "pending" | "accepted" | "rejected" }`.
  - `DELETE /StudentApplicationDelete/:id` — student withdraws an application (the older `/ApplyDelete/:id` no longer exists in the running backend).
  - Stored fields: `tuitionId, tuitionTitle, subject, classLevel, monthlyFee, deliveryMode, location, teacherId, teacherEmail, mentorName, studentId, studentName, studentEmail (lowercase), phone, sessionTime, message, status ("pending"), createdAt, updatedAt`.
